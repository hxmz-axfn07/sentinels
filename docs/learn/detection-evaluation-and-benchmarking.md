# Detection Evaluation and Benchmarking

## Scope

The evaluation feature measures the existing flow, rule, Isolation Forest, and hybrid engines. It does not change their detection thresholds, weights, or implementation. Results are stored as evaluation runs, separately from production analyses, security events, and incidents. A run is synchronous and bounded to one fixed synthetic dataset with at most five repeated passes.

## Dataset and labels

`sentinel-synthetic-flow-v1` is generated by Scapy using seed `1101`. The checked-in [manifest](../evaluation/dataset/manifest.json) describes every sample, its traffic recipe, parameters, split, ground-truth label, and expected rule categories. PCAP files are generated into a temporary directory and are not checked in.

There are 16 benign training captures and 27 independent test captures. The training partition contains ordinary TCP, UDP, ICMP, and incomplete-metadata recipes. The test partition contains 15 benign captures (including traffic near the port-scan threshold) and 12 suspicious captures: port scanning, SYN-heavy traffic, and repeated SYN tuples. Labels are assigned from the known recipe before any engine runs. Detection output is never used to create labels. Test and training sample identifiers are disjoint.

The evaluation unit is one capture. A capture is positive when its generator recipe intentionally emits one of the named suspicious patterns; otherwise it is negative. Flow-level labels are not inferred where a capture contains a mixture of flow roles. Synthetic traffic is a controlled functional benchmark, not a model of real network distributions.

## Metrics

For capture-level predictions:

```text
precision = TP / (TP + FP)
recall = TP / (TP + FN)
F1 = 2 × precision × recall / (precision + recall)
false-positive rate = FP / (FP + TN)
```

If a denominator is zero, the metric is `null`/undefined, not zero. Confusion matrices are returned in `[[TN, FP], [FN, TP]]` order. Rule-only is positive when its configured persisted rule run has at least one finding. ML-only is positive when at least one flow is labeled anomalous by the trained model. Hybrid is positive when the persisted assessment score is above zero. Hybrid score is an investigation-priority measure, not a probability of compromise.

## Engine configuration

The configured rule thresholds are recorded in each run. The benchmark compares them with a second configuration that doubles thresholds (bounded by the validated schema). Per-rule-category metrics use the recipe's independently assigned expected rule IDs. This compares behavior under the captured test recipes; it is not a general rule quality estimate.

Isolation Forest is freshly trained for each repeat using only the benign training captures, `flow-v1` feature schema, the existing preprocessing, 100 estimators, contamination `0.1`, `max_samples="auto"`, one worker, and the requested deterministic random seed. Training and test samples never overlap. The saved metadata includes the resulting model version, active features, sklearn version, and training sample counts. The usual estimator prediction is evaluated as ML-only. Additionally, fixed raw score thresholds `0`, `0.05`, and `0.1` are applied to the same persisted inference scores without retraining or selecting a threshold against test labels. Negative decision function is stored by SENTINEL as anomaly score; it is model-relative, uncalibrated, and not a probability.

Hybrid results use the normal persisted rule and inference outputs and the current application hybrid scoring configuration. No weights are changed to improve this benchmark. Severity and risk-score distributions are descriptive; scores do not estimate attack probability.

## Timing methodology

The harness separately measures packet metadata parsing, flow generation, rule execution, inference, hybrid assessment, model fitting, and per-test-capture end-to-end processing. Each requested repeat creates a fresh in-memory SQLite database, generates and ingests the training partition, fits a fresh model, then independently ingests and evaluates every test capture. Wall time and process CPU time are collected; mean and median are reported across observations. Capture generation and MySQL result persistence are excluded from per-stage processing times. Peak RSS is the process high-water mark before and after evaluation and cannot be attributed solely to the evaluation workload. Capture packet count, flow count, bytes, software versions, platform, and logical CPU count accompany timings.

These small synthetic results are not a production throughput or latency benchmark. Database choice, operating-system scheduling, workload shape, Python/scikit-learn builds, CPU, and system load affect timings. No cross-machine comparison is made.

## Persistence and API

Alembic revision `0009_evaluation_runs` adds one indexed run table with dataset version, seed, repeat count, state, timestamps, safe failure summary, and structured JSON result. It does not reference or alter analysis and incident rows. Synthetic PCAPs and temporary fitted artifacts are removed when the run ends. `POST /api/v1/evaluations` starts a run; `GET /api/v1/evaluations` lists runs with bounded pagination; `GET /api/v1/evaluations/{id}` returns one stored report. The frontend provides `/evaluation` and `/evaluation/{id}`.

The list endpoint returns paginated run summaries without the potentially large results document; the detail endpoint returns the full persisted report. The synchronous request may take longer than a reverse-proxy timeout. A persisted `running` state is written before computation; if the process exits, it can remain running because this milestone does not add a worker or recovery scheduler. Failures expose a generic safe summary while details remain in server logs.

## Current measured run

Evaluation run #1 was executed through the local API with three repeated passes. It used 16 training and 27 test captures, 52 training flows, and 128 test flows from 306 packets and 19,400 bytes. The model version was `8658cbcf-78bd-564c-908f-b7c45b6a185f` using scikit-learn 1.9.1. The complete metrics and environment are persisted by the API and rendered from that record.

| Configuration | TP | FP | TN | FN | Precision | Recall | F1 | False-positive rate |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Rule only | 12 | 0 | 15 | 0 | 1.000 | 1.000 | 1.000 | 0.000 |
| ML only | 12 | 4 | 11 | 0 | 0.750 | 1.000 | 0.857 | 0.267 |
| Hybrid | 12 | 4 | 11 | 0 | 0.750 | 1.000 | 0.857 | 0.267 |

The rule-only result reflects deliberately constructed patterns matching the configured rules. It should not be interpreted as field accuracy. ML and hybrid each marked four benign captures positive: two normal ICMP captures and two incomplete-metadata captures. The hybrid capture-level decision matched ML in this dataset. Doubling rule thresholds produced 4 TP, 0 FP, 15 TN, and 8 FN (recall 0.333): four port-scan and four SYN-heavy captures were missed. Repeated-SYN samples still had the port-scan indicator, although the stricter connection-attempt rule itself emitted no findings. That result makes the threshold sensitivity visible rather than hiding misses.

Fixed ML score comparisons were:

| Score threshold | TP | FP | TN | FN | Precision | Recall | F1 | False-positive rate |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `> 0.00` | 12 | 4 | 11 | 0 | 0.750 | 1.000 | 0.857 | 0.267 |
| `> 0.05` | 8 | 4 | 11 | 4 | 0.667 | 0.667 | 0.667 | 0.267 |
| `> 0.10` | 0 | 2 | 13 | 12 | 0.000 | 0.000 | 0.000 | 0.133 |

The hybrid severity distribution was 11 informational, 4 low, 8 medium, and 4 high; scores ranged from 0 to 61 with median 20 and P90 61. These are the engine's scores on the generated samples, not calibrated labels.

For the three repeated passes on this environment, median processing times per capture were 1.946 ms for packet parsing, 5.316 ms for flow generation, 2.106 ms for configured rule detection, 19.293 ms for inference, 8.347 ms for hybrid assessment, and 47.646 ms end-to-end. The measured end-to-end rates were 237.84 packets/s and 99.49 flows/s. Model-fit median was 120.633 ms across three fits. The recorded environment was Linux x86_64, Python 3.12.16, scikit-learn 1.9.1, and four logical CPUs; the OS did not report a processor model. These measurements are machine- and synthetic-workload-specific. They are not production performance claims.

## Limitations

- The dataset is small, synthetic, recipe-labeled, and shaped around known rule patterns.
- Capture-level labels do not establish individual flow ground truth.
- The benign near-threshold case is limited and does not cover the diversity of ordinary network behavior.
- Training data is known benign by recipe only; real training captures may contain anomalies.
- Threshold sweeps are illustrative and not calibration or test-set optimization.
- Hybrid binary evaluation uses score greater than zero, while severity is a separate prioritization output.
- No public labeled dataset, real-world traffic, or operational deployment has been evaluated.
- Synchronous execution is not suitable for unbounded large workloads and may be interrupted by HTTP timeouts.
